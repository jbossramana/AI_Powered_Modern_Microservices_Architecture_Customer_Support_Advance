# Concepts Guide — Intelligent Customer Support AI Gateway

This document explains the concepts independently of the README's run instructions. Each section describes the purpose, request flow, implementation class and a practical way to observe the feature.

## 1. AI Gateway

**Meaning:** An AI Gateway is the controlled entry point between client applications and one or more language models. It applies authentication, quotas, request validation, caching and usage measurement before model inference.

**In this project:** `ChatController` is the REST entry point. It calls `ApiKeyRateLimiter`, `TokenQuotaService`, `InputGuardService`, `PromptCacheService` and `SupportAiService`.

**Why it matters:** Clients should not call the model runtime without governance. A gateway gives a single place to apply policies and measure consumption.

## 2. API-key authentication

**Meaning:** A client sends a key identifying the application or integration. The gateway maps it to a configured client profile.

**Implementation:** `GatewayProperties` binds the `support.gateway.api-keys` map. `ChatController.client()` validates `X-API-Key`.

**Test:** Send a request with `X-API-Key: wrong-key`; the API returns HTTP 401.

**Production note:** The demo keys are plain YAML values. Use hashed keys or a secret manager, TLS, rotation and authorization policies in production.

## 3. Request rate limiting

**Meaning:** Restricts how many requests a client may make in a time window. This protects model capacity and prevents accidental request floods.

**Implementation:** `ApiKeyRateLimiter` maintains a fixed one-minute counter per API key using `ConcurrentHashMap` and `AtomicInteger`.

**Test:** The partner integration has a limit of five requests per minute. Repeated requests eventually return HTTP 429.

**Trade-off:** Fixed windows are easy to understand but can allow bursts around minute boundaries. A token bucket or sliding-window algorithm is preferable for a production gateway.

## 4. Token usage: prompt, completion and total

**Meaning:**
- **Prompt tokens:** tokens the model receives as input, including system instructions and conversation context.
- **Completion tokens:** tokens generated by the model.
- **Total tokens:** prompt plus completion tokens.

**Implementation:** `SupportAiService.reply()` obtains a Spring AI `ChatResponse` using `call().chatResponse()`. `UsageMetadataReader` reads usage metadata and extracts prompt, completion and total counts. `TokenUsageService` records the result.

**Important distinction:** Token counts are provider-reported metadata, not character counts. If the provider does not report usage, `tokenUsageAvailable` is false. The project must not invent a value.

**Test:** Call `/api/v1/chat` and inspect `promptTokens`, `completionTokens`, `totalTokens` and `tokenUsageAvailable`. Then query `/api/v1/usage`.

## 5. Token quota

**Meaning:** A client is allowed to consume only a configured number of tokens in a day. This is different from request rate limiting: one request can use many tokens.

**Implementation:** `TokenQuotaService` compares a client's daily quota with token usage recorded for the current local day. The quota is configured per client in `application.yml`.

**Test:** Query `/api/v1/usage/quota` with the client's API key.

**Limitation:** A true token quota depends on provider-reported token usage. If token metadata is unavailable, the system cannot know the exact consumption. This sample also uses in-memory, non-transactional accounting.

## 6. Cost calculation

**Meaning:** Estimates the cost of model use by applying configured prices per million prompt and completion tokens.

Formula:

```text
input cost  = prompt tokens     × input price  / 1,000,000
output cost = completion tokens × output price / 1,000,000
total cost  = input cost + output cost
```

**Implementation:** `TokenUsageService.cost()` uses `support.usage.input-cost-per-million` and `output-cost-per-million`.

**Test:** Call `/api/v1/usage/cost`.

**Important:** Ollama local inference does not issue a hosted-model invoice. The configured rates are illustrative comparison rates, not actual Ollama charges. Change the currency/rates to match the provider you want to model.

## 7. Usage ledger and analytics

**Meaning:** Each model request creates a usage event with request ID, client, model, timestamp, token counts, latency, cache state, status and estimated cost.

**Implementation:** `TokenUsageService` stores events in a bounded `ConcurrentLinkedDeque`.

**Analytics endpoints:**
- `/api/v1/usage` — summary.
- `/api/v1/usage/requests` — retained request events.
- `/api/v1/usage/clients` — aggregation by client.
- `/api/v1/usage/models` — aggregation by model.
- `/api/v1/usage/daily` — local-date aggregation.
- `/api/v1/usage/monthly` — month aggregation.
- `/api/v1/usage/latency` — average, P95 and P99.

**Limitation:** Detailed aggregations use the retained event window. When old events roll off, retained-window totals decrease. Process-lifetime request counters do not roll off.

## 8. Prompt caching

**Meaning:** If the same stateless prompt is asked again for the same model, return the earlier answer instead of invoking the model again.

**Implementation:** `PromptCacheService` normalizes prompt whitespace and case, uses model + prompt as the key, and stores values with a TTL.

**Why session requests bypass cache:** A session response depends on conversation history. Caching only the latest message could return an answer from a different conversation context.

**Test:** Send the same stateless chat request twice and inspect the `cached` flag. Query `/api/v1/cache/stats`.

**Trade-off:** Cache keys in this sample do not include client identity. For multi-tenant production use, consider tenant-specific cache namespaces and privacy requirements.

## 9. Conversation memory

**Meaning:** Stores recent user and assistant messages so a later turn can refer to earlier context.

**Implementation:** `ConversationMemory` stores a bounded list per `sessionId`. `SupportAiService` adds prior turns to the next prompt.

**Test:** Send the first request with session `S1001` stating an order number. In the second request, ask for that order number.

**Limitation:** This is simple in-memory prompt history, not Spring AI's persistent chat-memory repository. Data disappears on restart. Every retained message is sent as context, which increases prompt tokens.

## 10. Input guard: PII masking

**Meaning:** Detects selected personal-data patterns and replaces them before sending text to the model.

**Implementation:** `InputGuardService` uses regular expressions for email addresses, Indian mobile-number-like patterns and long card-number-like sequences.

**Test:** Submit a demo email and phone number in a chat request. The model receives redacted placeholders.

**Limitation:** Regex masking can miss formats and can produce false positives. It is not a certified PII detector. Do not send real customer data to this learning application.

## 11. Prompt-injection phrase check

**Meaning:** Attempts to block a small set of direct instructions that try to override the assistant's system prompt or reveal it.

**Implementation:** `InputGuardService` rejects two demonstration phrases.

**Test:** Submit a message containing `ignore all previous instructions` or `reveal your system prompt`.

**Limitation:** This is a teaching example, not robust prompt-injection protection. Attackers can rephrase or encode instructions. Production systems need layered controls, trust boundaries, tool authorization and output validation.

## 12. System prompt and AI orchestration

**Meaning:** The system prompt defines the assistant's role, tone and behavioral constraints. The orchestration service assembles context and invokes the model.

**Implementation:** `SupportAiService` builds a `ChatClient` request with a system message and user prompt. Session history is appended for conversational requests.

**Why it matters:** Keep orchestration logic in a service rather than putting model calls and prompt rules inside REST controllers.

## 13. Structured ticket classification

**Meaning:** Instead of asking the model for free-form prose, ask for a structured Java object with known fields.

**Implementation:** `SupportAiService.classify()` uses `.entity(Classification.class)` to map the model output into category, priority, confidence and rationale.

**Test:** Call `/api/v1/tickets/classify`.

**Production note:** Validate allowed category and priority values, confidence bounds and rationale before acting on the result. The sample classification endpoint is not yet included in token usage ledger accounting.

## 14. Streaming with Server-Sent Events

**Meaning:** The server sends generated text chunks as they become available rather than waiting for the complete answer.

**Implementation:** `SupportAiService.stream()` uses `ChatClient.stream().content()`. `ChatController` exposes it as `text/event-stream`.

**Test:** Use `curl.exe -N` with `/api/v1/chat/stream`.

**Trade-off:** Streaming improves perceived responsiveness, but usage aggregation and cancellation handling need additional work. The sample does not include stream token accounting.

## 15. Feedback

**Meaning:** Allows a caller to rate an answer, typically on a 1–5 scale, and optionally leave a comment.

**Implementation:** `FeedbackController` validates and stores the latest 500 feedback entries in memory.

**Test:** POST a request ID and rating to `/api/v1/feedback`, then GET the endpoint.

**Future extension:** Join feedback with request usage events for model quality and cost analysis.

## 16. Observability: Micrometer and Actuator

**Meaning:** Observability lets operators inspect service health, request volume, errors, latency and custom business metrics.

**Implementation:** `TokenUsageService` registers counters and timers with Micrometer. Spring Boot Actuator exposes them.

**Useful endpoints:**
- `/actuator/health`
- `/actuator/metrics`
- `/actuator/metrics/support.requests`
- `/actuator/metrics/support.request.duration`
- `/actuator/metrics/support.tokens.total`
- `/actuator/prometheus`

**Important:** The Prometheus endpoint is an export format. A Prometheus server is not bundled or required for local testing.

## 17. Latency and percentiles

**Meaning:** Average latency is the arithmetic mean. P95 is the value below which 95% of recorded requests fall; P99 is the corresponding 99th percentile.

**Implementation:** `TokenUsageService.latency()` calculates these from retained request events.

**Why percentiles matter:** An average can hide slow outliers. P95/P99 help identify the slowest user experiences.

**Limitation:** These are simple retained-event calculations, not a replacement for a long-term histogram or distributed tracing system.

## 18. In-memory architecture

**Meaning:** Application state lives in JVM collections rather than a database or external cache.

**Implementation:** `ConcurrentHashMap`, `ConcurrentLinkedDeque`, `AtomicInteger` and `LongAdder` are used by the services.

**Advantages:** Simple setup, no Docker and no infrastructure dependency.

**Disadvantages:** State is lost at restart, not shared across multiple application instances, and memory use must be bounded.

## 19. What a production evolution would add

The sample intentionally keeps infrastructure local and understandable. A production evolution would consider:
- Secret manager and robust authentication/authorization.
- Distributed rate limiting and quotas.
- Persistent usage and conversation storage.
- Transaction-safe quota reservation.
- Robust prompt-injection and PII detection.
- Circuit breaker, bounded retry and request timeouts.
- Model routing and fallback.
- Stream usage aggregation and cancellation.
- Dashboards and alerting.
- Distributed tracing.
- Automated integration tests and load tests.

## 20. Suggested teaching sequence

1. Start with a direct ChatClient call.
2. Add API-key authentication.
3. Add request rate limiting.
4. Read `ChatResponse` and inspect token metadata.
5. Record usage in `TokenUsageService`.
6. Add per-client and daily usage aggregation.
7. Calculate illustrative costs.
8. Add prompt caching and compare model calls.
9. Add session memory and observe prompt-token growth.
10. Add PII masking and prompt guard.
11. Add structured classification.
12. Add streaming.
13. Add Micrometer and Actuator.
14. Add feedback and discuss quality analytics.

This sequence demonstrates the evolution from a basic LLM call to a governed AI gateway.
